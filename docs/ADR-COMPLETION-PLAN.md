# ADR completion plan

**Date:** 2026-10-11
**Basis:** `main` at `b322455`, every ADR in `docs/adr/`, the four execution specs, the PRDs, the research notes and the Shibboleth prototype results.
**Purpose:** say what has to happen, in what order, for every decision in ADR-0001 to ADR-0011 to be fully implemented, and what the owner has to do outside the code.

## How this plan was produced

Each ADR, plus the ADR set as a document set, was audited against the repository: every clause of each Decision section, every follow-up, and every item in the spec that implements it was traced to code, Terraform, workflows or documents, and given a status. A second reviewer then tried to refute each status by re-reading the code, and a third looked for clauses the first had missed. The verified result is 618 items across the twelve subjects. This plan carries the substantive ones; the per-item evidence is not committed.

Three facts about the snapshot matter when reading it:

- Eleven other sessions were working in this repository at the time, all on CI, git-hook and secret-name fixes. Their merged work (pull requests 82 to 93) is reflected here; none of them touches ADR implementation. Section 6 lists what is in flight so nobody duplicates it.
- Nothing from the platform Terraform root has ever been applied in AWS. The dev account holds the bootstrap state buckets, the GitHub OIDC provider and a hosted marketing preview; the prod account has nothing.
- The five amendments made when the ADRs were ratified on 2026-10-10 were written into the ADRs but not into the specs or PRDs, so the execution documents currently describe the superseded design in five places. Fixing that is step 1.

## 1. Where the decisions stand

Ten ADRs are Accepted and one (ADR-0007, identity) is Proposed and on hold. Weighted by the work each decision implies, the set is roughly 12 to 15 percent implemented. Only the two deployment-shaped decisions have real code: the marketing site is code-complete and previewing on CloudFront, and the multi-account Terraform layout is written. The product core has no implementation: there is no content-hash cache, no page-parallel state machine, no engine adapter, no evidence pack, no triage engine, no Aurora, no row-level security, no tenant isolation and no Bedrock layer. The 2025 mocks are still the live pipeline: `tag_pdf` returns a fixed tag count, `validate` returns a fixed score, and the worker uploads the original file as the "accessible" PDF and writes literal scores to the document record.
